# Security and privacy audit — 2026-08-25

Scope: the whole overlay (`src_overrides/bedrock/`, `patches/`, `build/`) at
commit of PR #40, read against the checklist in the audit request (10 blocks,
fingerprinting through performance).

## 0. The finding that governs every other one

**No renderer-side protection exists in this project, at all.** The tree
contains exactly two patches against Chromium —
`patches/bedrock/build/0001-add-bedrock-to-chrome-browser.patch` (build wiring)
and `patches/bedrock/integration/0001-bedrock-startup-hook.patch` (two call
sites in `browser_ui_prefs.cc` and `renderer_preferences_util.cc`). Nothing
touches Blink, V8, `//content`, `//net` or `//services/network`.

Therefore every request in the audit of the form "check that
`canvas.toDataURL()` is blocked / `getChannelData()` is modified /
`document.fonts.check()` is constant / `navigator.getBattery()` is pinned /
`DeviceOrientationEvent` is off / ICE candidates are mDNS-only" has the same
answer: **there is no code that could do it.** What exists is a policy table
(`privacy/fingerprinting/fingerprint_policy.cc`) that says which *strategy*
each of 21 surfaces should get at each level, and host tests that check the
table. A table is not an interception.

The project's own documents already say this, and they say it accurately —
`docs/ACCEPTANCE.md` (11 of 31 criteria met), `build/ENFORCEMENT.md` (one
feature enforced: `webrtc_policy`), `docs/PHASES.md` (phases 3–15 not started).
This audit confirms those documents rather than contradicting them. It also
means one framing in the request has to be rejected outright:

> "BEDROCK BROWSER — браузер с максимальной анонимностью"

Bedrock is not an anonymity browser and its own non-negotiable #5 forbids the
claim. It is a privacy-hardened Chromium overlay in which one protection is
currently live. Anything stronger is marketing that the code cannot back.

**Verdict legend used below**
`OK` — verified by reading the code *and* an executing test ·
`WEAK` — implemented, but with a defect or an unsupported claim ·
`NOT WIRED` — logic exists, no engine runs it ·
`STOCK` — whatever Chromium does; Bedrock neither improves nor breaks it ·
`ABSENT` — no code exists.

## 1. Fingerprinting (audit block 1)

| Surface | Requested check | Verdict | Evidence |
| --- | --- | --- | --- |
| Canvas | `toDataURL`/`toBlob` blocked | ABSENT | no shim; policy row says farble at 1–2, block at 3 |
| WebGL | `readPixels` sanitised, per-launch variation | ABSENT | as above |
| Audio | `getChannelData`, `AnalyserNode` | ABSENT | as above |
| Fonts | fixed font set, `document.fonts.check` constant | ABSENT | as above |
| Screen/window | fixed values, letterboxing | NOT WIRED | `QuantizeWindowSize()` + `ComputeLetterbox()` host-tested (PR #41) |
| Timezone/language | UTC, `en-US` | NOT WIRED | `NormalizedTimezone/Language()` |
| WebRTC | no local IP, mDNS only | **OK (partially)** | the only enforced feature: build 2 hands `default_public_interface_only` to renderers |
| Battery | pinned value | ABSENT | policy says block at ≥1; nothing blocks it |
| Orientation/Motion | disabled | ABSENT | `sensors` row says block; nothing blocks it |

Two requested behaviours are also **wrong as goals**, and the code is right to
refuse them:

* *"different fingerprint data on every launch"* and *"`devicePixelRatio`
  randomised"* — per-call/per-launch randomness is itself an identifier and is
  averaged out by repeated sampling. `SurfaceSeed()` is deliberately stable
  within a session (ADR 0008, rule 2). Keep it that way.
* *"`screen.width` always 1920×1080 regardless of the real screen"* — reporting
  a size the window does not have is recoverable with one
  `getBoundingClientRect()`. The design (render into the reported box) is
  correct; see `docs/design/050-letterboxing.md`.

**F4 (High, cryptographic — fixed in PR #43).** `SurfaceSeed()` derives noise seeds as
`Mix(Mix(session_secret ^ FNV1a(site)) + surface + 1)` with splitmix64's `Mix`.
`Mix` is a **bijection** and both constructions are public and unkeyed, so a
site that recovers its own seed from observed noise can invert it and obtain
`session_secret` — a value shared by every site in the session. Two colluding
sites each recover the same 64-bit number and link the user perfectly *within a
session*, which is the exact property the design says the per-session secret
provides. Also, `SeededUnit(seed, index) = Mix(seed + index)` lets streams of
different surfaces/sites overlap when `seed_a + i == seed_b + j`.

Fix (sketch — needs a real PRF, not a mixer):

```cpp
// One-way, keyed, domain-separated. Bedrock has no crypto library of its own,
// so this belongs in the Chromium build against BoringSSL:
//   sub_key = HKDF-SHA256(master_secret, salt = "bedrock/fp/v1", info = site)
//   seed    = HMAC-SHA256(sub_key, surface_id) truncated to 64 bits
//   stream  = HMAC-SHA256(sub_key, surface_id || counter)
// Properties gained: recovering one site's seed reveals nothing about the
// master secret or any other site (one-wayness), streams cannot overlap
// (domain separation), and master_secret becomes 256-bit.
```

Until that exists, `session_secret` must be treated as **linkable within a
session** and the disclosure text for canvas/WebGL/audio should not imply
otherwise.

## 2. Network (audit block 2)

| Item | Verdict | Note |
| --- | --- | --- |
| Tor transport | NOT WIRED | `session/browsing_mode`: SOCKS stream isolation per top-level site (`socks_username = site`, password = epoch) is the right mechanism; no Tor process, no proxy plumbing exists |
| DNS through Tor / no system DNS | NOT WIRED | `dns_through_proxy` is a flag in a config struct |
| DoH/DoT | NOT WIRED + **WEAK** | see F6 |
| Headers / UA / Accept-Language | ABSENT | no header rewriting anywhere in the tree |
| Referrer policy | ABSENT | still on the research queue |
| HSTS / HTTPS-Only | NOT WIRED + **WEAK** | see F1, F2 |
| Cookie isolation, 3p cookies | NOT WIRED | `privacy/storage/storage_isolation` + `security_levels`; note that from Strict the design *keeps* first-party cookies and makes storage ephemeral — blocking them outright was rejected in PR #39 |

**F1 (Critical, fixed in this change).** `HttpsPolicy::IsLocalOrOnion()`
classified hosts by string prefix:

```cpp
StartsWith(host, "127.") || StartsWith(host, "192.168.") ||
StartsWith(host, "10.")
```

`10.example.com`, `127.evil.test` and `192.168.attacker.net` are **registrable
domain names**. Any of them was treated as a local address, which means: no
HTTPS upgrade, no HTTPS-Only interstitial, plaintext load, silently. An attacker
buys one name and gets a permanent downgrade path for every Bedrock user.
Fixed by parsing an IPv4 literal and testing the octets (plus 172.16/12,
169.254/16, IPv6 loopback/ULA/link-local, and label-boundary matching for
`.local`/`.onion`/`.internal`). Seven attacker-registrable names and nine real
local addresses are now asserted in `https_policy_test.cc`.

**F2 (High, fixed in this change).** In `ForNavigation()` the per-site shields
value was read *before* the mode, so `Control::kHttps = Value::kAllow` on a host
returned `kAllowPlaintext` even while the profile was in HTTPS-Only — directly
contradicting the comment in `ModeForHost()` ("a site cannot opt itself out of
HTTPS-Only"). Order is now: local/onion → explicit per-host exception →
HTTPS-Only → shields → upgrade. The explicit exception (the user clicked
through an interstitial) is still honoured; the shields toggle is not.

**F6 (Medium, partly fixed).** `DnsSettings::SetStrict(true)` returned `void`
and did nothing when the system resolver was selected — so a settings surface
could show "strict, fail-closed" while queries went to the OS resolver in
plaintext. It now returns `bool` and the refusal is asserted. Still open in the
same file: the `dns0.eu` preset carries `https://dns0.eu/` as its DoH template,
which is the website, not a DoH endpoint (`https://zero.dns0.eu/` and
`https://open.dns0.eu/` are). A preset that fails to resolve plus the default
`FallbackPolicy::kSystemWithWarning` equals plaintext DNS while the UI says
"encrypted". Two follow-ups: verify every template against its operator's
documentation, and add a gate that a template contains a path (a bare origin is
almost always the marketing site).

**F5 (High, fixed in this change).** `KeysToClearForSite()` matched
`key.top_level_site == site` only. Data the site wrote **while embedded on other

`shop.test` — survived "Clear this site" and "Forget about this site". The
identifier the user asked to delete stayed on disk. `StorageKey` now carries

## 5. Crypto and storage (audit block 5)

| Item | Verdict | Note |
| --- | --- | --- |
| Certificate validation, no bypass switch | OK (policy) + STOCK | `Proceedable()` refuses revoked / pinned-mismatch / weak-signature outright; `advanced_settings` guard G9 refuses any setting that would disable validation. Chromium does the validating |
| TLS 1.3 only, PFS, OCSP | ABSENT | no TLS configuration code exists. "TLS 1.2 disabled" is also a bad goal: it breaks a large share of the web for no privacy gain |
| Password encryption AES-256-GCM | **WEAK** | see F3 |
| Master password mandatory | NOT A GOAL, and currently broken | see F3 |
| Encrypted profile on disk | ABSENT | no code; Chromium's on-disk data is not encrypted at rest beyond the platform keystore for secrets |

**F3 (Critical — fixed in PR #43, design rewritten).** `PasswordStore::Unlock(master)`
verifies the master password by re-encrypting a known string and comparing
ciphertexts:

```cpp
const std::string verifier = cipher_->Encrypt("bedrock-verifier:" + master_password);
if (master_password_verifier_.empty()) master_password_verifier_ = verifier;  // TOFU
if (verifier != master_password_verifier_) { /* reject */ }
```

Three defects in five lines:

1. **The master password is not a key.** Entries are encrypted by the injected
   cipher (the platform keystore) regardless of it, so anything that can reach
   the keystore — any process in the user's session — decrypts every password
   without knowing the master password. It is a UI gate presented as
   protection.
2. **It cannot work with real AEAD.** Comparing ciphertexts requires a
   deterministic cipher. AES-256-GCM is randomised per nonce, so the first real
   cipher makes *every* correct password fail. The host test's fake cipher hides
   this — the classic "test double proves the wrong thing".
3. **Trust-on-first-use.** With an empty verifier, whatever password arrives
   first *becomes* the master password, and no wrong-password path exists on a
   fresh profile.

Fix (envelope encryption, in the Chromium build against BoringSSL):

```cpp
// Stored: salt, KDF params, wrapped_data_key, verifier_tag.
// 1. kek        = Argon2id(master_password, salt, m=64MiB, t=3, p=1)   // memory-hard
// 2. data_key   = 256 random bits, generated once per store
// 3. wrapped    = AES-256-GCM(kek, data_key, aad = "bedrock/pw/v1")
// 4. Unlock: derive kek, AES-GCM-open(wrapped) -> data_key. The GCM tag *is*
//    the verifier, so verification is authenticated, not a string compare, and
//    a wrong password fails to open instead of matching a stored blob.
// 5. Entries are encrypted under data_key, which only exists in memory while
//    unlocked, and the keystore protects `wrapped` at rest.
```

Also: `Sha1Hex()` is hand-rolled SHA-1 in a browser repository, contradicting
the file's own "crypto belongs to the platform" rule. It is only used for the
k-anonymity prefix, but it should be BoringSSL's once the build exists.

## 6–8. JavaScript, attack surface, performance (audit blocks 6–8)

Everything requested here is **stock Chromium**, and that is the correct
answer, not a gap: site isolation, the sandbox, CSP enforcement, XSS/Spectre
mitigations, Service Worker and WebAssembly isolation, X-Frame-Options,
SameSite defaults. Bedrock adds one rule *about* them —
`privacy/security/security_baseline` fails the build if a privacy feature
weakens a Chromium mechanism (invariant 13) — and its own `security_baseline`
test enumerates forbidden switches. Notes on the specific asks:

* "браузер не выполняет инъекции через `eval()`" — a browser must run `eval()`;
  removing it breaks the web. Not a defect.
* "все формы используют CSRF-токены" — a browser cannot add CSRF tokens to
  sites' forms; SameSite cookies are the browser-side control.
* Phishing/malware protection: **deliberately absent.** `safe_browsing_mode=0`
  in the release args, because Safe Browsing is a server-side lookup service and
  the project runs no server (non-negotiable 1). That is a real, stated
  trade-off, not an oversight — the user gets no phishing protection.
* Memory leaks / CPU / startup / memory budgets: 7 metrics are measured on every
  commit; **8 budgets (startup, memory, idle CPU, network overhead, JS
  benchmark) have no numbers** and are marked `pending` because they need a
  build. Do not quote them.
* Cross-platform: built and run on **Linux x64 only**. Windows is documented,
  never built; macOS is best-effort. `platform_support` refuses to call a
  platform supported until it is built, tested and released.

## 10. Recommendations, in the order they buy the most

1. **Stop adding subsystems; wire the existing ones.** The gap between
   "host-tested" and "enforced" is the entire product. `docs/PHASES.md` and
   `build/BUILD_ON_YOUR_MACHINE.md` already price it.
2. ~~Fix F3 and F4 before either subsystem is wired~~ — **done**, see
   `docs/design/051-crypto-primitives.md`. Both were key-derivation designs that
   a later port would have preserved verbatim.
3. **Do not weaken the honesty layer.** `ACCEPTANCE.md`, `ENFORCEMENT.md` and
   the `Status::kEnforced` gate are what made this audit possible in an hour;
   the tempting shortcut ("mark it done, it is tested") destroys that.
4. **Add a gate for the class of bug F1 belongs to**: no security decision may
   be made by `StartsWith`/`EndsWith` on a host. Prefix matching on hostnames
   is a recurring vulnerability pattern, not a one-off mistake.
5. **Correct the product framing** wherever "maximum anonymity" appears in
   briefs: the code cannot support it, and the project's own rules forbid it.

## Addendum, same day — recommendation 4 and finding F10

Recommendation 4 was "make F1 unrepeatable rather than fixed". Grepping for the
shape rather than the symptom turned up **three** independent implementations of
"is this host inside that domain" — in `https_policy.cc`, `filter_engine.cc` and
`url_cleaner.cc` — each subtly different, and one of them (F1) wrong.

They are now one function. `src_overrides/bedrock/privacy/network/host_match.h`
is the only place in the tree that compares a host name to anything, and
`scripts/check_host_matching.py` fails the build if a prefix/suffix decision on
a host-shaped variable appears anywhere else. The gate's own self-test contains
the original F1 line, so the specific bug cannot come back either.

Consolidating them exposed **F10 (Medium, live)**: filter rules were lowercased
when parsed, but the *request* host was compared in wire form. Host names are
case-insensitive and may carry a trailing root dot, so `EVIL.com/track.js` and
`evil.com./track.js` matched no domain-scoped rule at all — a filter bypass
needing nothing but a differently spelled name. `NormalizeHost()` now runs on
both sides of every comparison. The reverse case is also fixed: a rule written
`Example.COM` matches, instead of silently matching nothing.

Two comparisons were deliberately *not* moved: the `https://` scheme checks in
`https_policy.cc` and `dns_settings.cc`. Those are URL schemes, not hosts, and
they are now named `HasScheme()` so that neither a reader nor the gate mistakes
them for host logic.
